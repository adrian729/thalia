# Thalia — issues to check

1. ~~**AudioContext never gets unlocked/resumed on mobile.**~~ **DONE.** Added `src/audio-context/useAudioUnlock.ts`, a new hook (same shape as the other `use*.ts` hooks in `src/audio-context/`) wired up in `MainAudioContextProvider.tsx` right after `useAudioSetup`. It covers both failure modes: (1) a `pointerdown`/`keydown` listener on `window` calls `audioContext.resume()` on the first real gesture if the context isn't already `'running'`, then removes both listeners so nothing lingers for the app's life; (2) a `visibilitychange` listener plus `audioContext.onstatechange` re-resume the context whenever the tab becomes visible and the state is `'suspended'` or iOS's `'interrupted'` (not in TS's `AudioContextState` type, checked via a string comparison). `README.md:36` updated to describe the actual behavior ("unlocks on the first key press or pointer press") instead of the old, never-implemented "click anywhere" text. Verified: `pnpm exec tsc -b` and `pnpm exec vite build` both clean, and `npx eslint .` shows the exact same 5 pre-existing prettier errors + 1 warning as before the change (no new lint issues introduced).

2. ~~**`audio.ts` never disconnects the downstream gain/filter nodes each note creates.**~~ **DONE.** Every `play*` function in `src/utils/audio.ts` now disconnects its downstream `GainNode`/`BiquadFilterNode`s once the note/hit finishes, matching the `oscillator.onended = () => gainNode.disconnect()` pattern already used in `useOscillator.ts:61-63`. For functions with a single terminal source node (`playSynthOscillator`, `playTom1`, `playTom2`), the source's own `onended` disconnects the downstream chain directly. For functions with multiple source nodes feeding the same downstream nodes (`playKick`, `playSnare`, `playHihat`, `playCymbal1/2/3`, `playTom3`), a shared counter decrements on each source's `onended` and disconnects the shared downstream nodes exactly once, after the last source ends. `playSynth` has no source node of its own (it only wraps `playSynthOscillator` calls, each of which cleans up its own gain node) — its `gainControl` is disconnected via a `setTimeout` keyed to the note's `duration` instead. No envelope/timing/audible behavior was changed. Verified: `pnpm exec tsc -b` and `pnpm exec vite build` both clean, and `npx eslint .` shows the exact same 5 pre-existing prettier errors + 1 warning as before the change (no new lint issues introduced).

3. **`DrumPad.tsx:101-104` double-connects its bus under StrictMode.** The effect calls `destinationRef.current.connect(dry)` / `.connect(wet)` with no cleanup function, unlike every other `.connect()` effect in the codebase (`useReverb.ts:74-79`, `ThaliaPad.tsx:53-56`, `useAnalyser.ts:36-38`, all of which disconnect on unmount for this exact reason). Since `main.tsx` wraps the app in `<StrictMode>`, dev mode mounts→unmounts→remounts once, so the drum bus ends up connected to `dry`/`wet` twice — audibly doubled drum volume in dev. **Fix:** return a cleanup that disconnects, matching the other three call sites.

4. **`DrumPad.tsx:92` allocates a throwaway `GainNode` every render.** `useRef(new GainNode(audioContext, { gain: 1 }))` — the `new GainNode(...)` expression runs on every render (only the first result is kept), which is the exact anti-pattern `useLazyRef.ts`'s own doc comment names and that every other component (`ThaliaPad.tsx:35-37`, `useAnalyser.ts:15-23`, `useReverb.ts:48-59`) avoids by using `useLazyRef`. **Fix:** swap to `useLazyRef(() => new GainNode(...))`.

5. **`useReverb.ts:82-100` (`setSelectedIR`) has an async race and no error handling.** The `fetch → arrayBuffer → decodeAudioData` chain has no abort/ignore-flag and no `.catch()`. Switching reverb type quickly (one click per IR via `ThaliaPadOptions.tsx:71-80`) can let an older fetch resolve after a newer one and silently overwrite `convolverRef.current.buffer` with the stale IR; a failed fetch/decode (offline, 404) becomes an unhandled promise rejection with no user-visible fallback. **Fix:** guard with an abort controller or a "latest request wins" token, add `.catch()`.

6. **`notes.ts:961-966` has an out-of-spec entry.** Last table entry is `{ midiId: 128, octave: 9, ... }`, but MIDI is only defined 0–127. Currently unreached by the app, but it's a landmine for anything that later assumes the table covers exactly the MIDI range. **Fix:** delete the 128 entry (127 is already the correct last MIDI note).
